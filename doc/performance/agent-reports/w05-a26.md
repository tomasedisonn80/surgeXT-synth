# Wave 5 — agent 26: platform and build portability review

Role: systems engineer and VST specialist. Scope: read-only review of the current
production diff, optional performance targets, presets and existing release
matrix. No native compilation or benchmark was performed by this agent.

## Findings

No new source-level platform compile blocker was found in this review.

- **C++ and headers:** Root `CMakeLists.txt` already selects C++20. The added
  `std::bit_cast` calls therefore use the existing language requirement; the
  pinned `sst-basic-blocks` dependency also already uses `std::bit_cast` in
  `dsp/PinkNoise.h`. Each changed implementation explicitly includes `<bit>`.
  Effect headers include `Effect.h`, which includes `SurgeStorage.h`; that header
  explicitly provides `<cstdint>` and `<atomic>` for the new fields.
- **Atomics:** `coefficientTableGeneration` uses the same 64-bit atomic family
  already present in `SurgeStorage` for patch/tuning/order generations. Standard
  atomic alignment is retained; no packed or externally supplied storage is
  introduced. Relaxed reads occur at coefficient-control cadence, and the only
  new read-modify-write occurs when `init_tables()` completes. This source review
  does not certify lock freedom on every toolchain, particularly the existing
  lightly tested Windows 32-bit configuration. Do not add an unconditional
  lock-free static assertion that would gratuitously remove that configuration.
- **DSP portability:** No new architecture-specific intrinsics, `-march=native`,
  AVX requirement or fast-math mode was introduced. The existing x86 SSE4.1 and
  ARM SIMD selection remain in place. Hoisting the common lowcut omega preserves
  its `double` result type. Cached floating-point inputs use fixed-width integer
  bit representations, which match the existing supported float/double targets.
- **Plugin defaults:** Performance tools are opt-in and link only to
  `surge-common`; their Python 3.10 requirement is confined to that option.
  Normal plugin configurations retain their JUCE test dependency. The headless
  test allowance is constrained to explicit performance builds. The new
  `sampleRateReset()` overrides match the existing virtual base signature.
- **Presets:** Schema 3 matches the repository's CMake 3.22 minimum. Ninja,
  Release, LTO and two build workers are explicit. `cpu-release` preserves the
  existing default Lua selection; `cpu-headless` intentionally selects PUC Lua
  for reproducible headless validation. Neither change supplies new evidence
  that merely selecting Release/LTO improves an already optimized build.
- **PCM tools:** Both native tools open PCM streams in binary mode and encode
  the float bit pattern into explicit little-endian bytes. File hashes therefore
  do not depend on native byte order or Windows text translation. This does not
  imply that different platforms or compilers must produce identical DSP output.

## Documentation requirements communicated to the coordinator

`cpu-release` uses the selected compiler environment and target architecture. It
is not a substitute for the complete release matrix:

1. Windows Ninja builds need an initialized compiler environment. Windows
   ARM64/ARM64EC builds need an explicit `-DSURGE_LUA_IMPL=puc`, as used by the
   existing release workflow; `libs/lua/README.md` explains why LuaJIT does not
   build for those targets.
2. A macOS universal build needs the existing explicit
   `-DCMAKE_OSX_ARCHITECTURES="arm64;x86_64"` setting. The preset alone builds the
   compiler's selected architecture.
3. Measurements from the headless PUC configuration must retain that label;
   they do not establish LuaJIT or every plugin-host performance result.
