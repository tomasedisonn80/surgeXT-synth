# Agent 47 / wave 8 — optional render-thread CPU timing

Role: systems engineer and VST performance instrumentation specialist.
Implemented an opt-in Linux thread CPU sidecar in
`src/performance/CpuBenchmark.cpp`; no production DSP or plugin code changed.

## Reason for the measurement

The first shared-machine wall-time experiment did not resolve a broad CPU gain.
Wall time includes delays while the rendering thread is not scheduled. The new
measurement records the CPU time consumed by that same rendering thread,
separately from the retained wall-time result. This is additional instrumentation,
not evidence that any optimization is faster.

## Native interface and timing boundary

```sh
surge-cpu-bench --output wall.json --thread-output thread.json \
  --sample-rate 48000 --repetitions 1 --seconds 30 --tail-seconds 5
```

`--thread-output` is optional and defaults to disabled. When absent, the executable
does not query the thread CPU clock. When present, it verifies Linux
`CLOCK_THREAD_CPUTIME_ID` availability before opening any output. Unsupported
platforms and clock failures return an explicit error. The installed Linux
`bits/time.h` identifies this clock as the thread-specific CPU-time clock.

Each CPU interval starts immediately before the existing steady-clock start read
and ends immediately after its end read. It therefore includes engine processing,
preallocated PCM copies, transport advancement, the two wall-clock reads and the
small instrumentation overhead around them. Setup, MIDI note-on/off events,
file I/O, fingerprints and statistics remain outside the interval. The clock
excludes CPU consumed by other threads and time spent waiting to be scheduled.
Every recorded CPU interval must be finite and strictly positive.

The existing schema-1 wall report, its timer placement and its audio evidence
remain unchanged. The optional sidecar records a separate timing unit rather
than putting CPU values in fields named `wall_seconds`.

## Sidecar contract

The exact root fields are:

- `schema`: `1`
- `tool`: `surge-cpu-bench-thread-clock`
- `clock`: `CLOCK_THREAD_CPUTIME_ID`
- `sample_rate`, `repetitions`, `frames`, `block_size`, `channels`, `seed`
- `scenarios`
- `ok`

Every scenario has exactly `name`, `held_audio_seconds`, `tail_audio_seconds`,
`pcm_hashes`, `held_thread_cpu_seconds`, and `tail_thread_cpu_seconds`.
All three arrays follow the repetition order of the companion wall report.
The PCM hashes bind the sidecar to that report's actual rendered audio.
`ok` is true only after successful positive finite timing and deterministic
repetitions. A clock or write error cannot produce a successful process exit.
Agent 48 received this contract for strict validation and paired-runner support.

## Output protection

The pre-open path check rejects the thread sidecar if it aliases the input patch,
wall report, or any generated PCM file. It uses the existing canonical-path and
filesystem-equivalence checks, covering direct paths, symlinks and hardlinks.
An explicitly empty thread-output argument is rejected. No output is opened until
argument, clock, fixture and alias validation succeeds.
