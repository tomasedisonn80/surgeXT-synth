# Wave 4 / Agent 21 — benchmark and comparison audit

Role: systems engineer and VST performance specialist. Read-only review of
`CpuBenchmark.cpp`, its CMake target, `CMakePresets.json`, and `compare.py`.

## Concrete correction required

`--patch FILE --output FILE` currently validates the input, then opens and truncates
the output before the fixture is loaded. The report can also collide with a
generated `<scenario>.f32` inside `--pcm-dir`. Reject canonical/equivalent input
and output collisions before opening either output, including symlink and existing
hard-link aliases. The coordinator accepted this finding for integration; this
review does not claim the correction or native negative tests have passed.

## Verified source behavior

- The conditioner, EQ3 and EQ11 scenarios select an actual global effect slot
  through `setParameter01`, run the loader, and require both the effect object and
  expected type. They use nontrivial gains; Conditioner explicitly activates its
  side highpass. Native execution must still confirm the new scenarios.
- Every repetition constructs a fresh engine. Seeds are reapplied after the
  128-block preroll and before note-on. Rendering uses the same FPU guard as synth
  callbacks. All samples are checked for finiteness; repeated fingerprints must
  match. One repetition only establishes a smoke result, not repeatability.
- Timed windows contain engine processing, PCM copies and transport advancement.
  Setup, file I/O, note events, hashes and statistics are excluded. Held timing
  includes the first active blocks, so describe it as an onset-inclusive offline
  workload, not a pure warmed steady-state or host-deadline measurement.
- Numeric bounds prevent nonfinite rates/durations and unbounded buffer sizes.
  The comparator checks scenario sets, reported durations, summaries, repetition
  fingerprints and optional complete PCM bytes. Its explicit limitations are
  appropriate. Prefer full PCM verification for published evidence.

## Evidence limitations to retain

The report records **requested** Lua/LTO settings, not a complete effective build
description. Empty Lua selection can resolve to LuaJIT or the legacy no-Lua path;
LTO can be disabled elsewhere despite the request. Compiler name/configuration
also cannot distinguish custom optimization flags. Use explicit matched settings
and retain effective flags/cache, harness and binary hashes, and source snapshots
in the orchestration evidence.

Patch identity is only a path; neither patch bytes nor `--data` contents are
bound to the report. Engine construction also reads user defaults and initializes
MTS-ESP, so ambient settings or an external tuning master can affect a run.
Record fixture hashes and environment assumptions, and keep baseline/candidate
runs paired in the same controlled environment. Matching PCM detects audible
differences but does not by itself establish identical configuration or hardware.
