## Processor test API and behavior review

`src/surge-xt/xt-tests/CMakeLists.txt` explicitly includes the new source and links
the existing `surge-xt`, Catch 3 and JUCE test dependencies. The source uses the
same isolated user-data/PatchDB setup pattern as the existing MIDI tests.

Inspected API declarations and source support the following uses:

- `File::createDirectory()` returns `Result`, supporting `.wasOk()`.
- `AudioBuffer::setDataToReferTo(Type* const*, int, int)` accepts the guarded
  external channel pointers, including the zero-frame case with valid storage.
- `AudioBuffer::getMagnitude(startSample, numSamples)` is the all-channel overload.
- `AudioProcessor::setBusesLayout()` and `setRateAndBufferSizeDetails()` are public.
- `SurgeSynthProcessor::inputIsLatent`, synthesizer voices and required engine
  fields are accessible; `SurgeSynthesizer.h` includes the complete voice type.
- Current bus validation accepts disabled/mono/stereo input and either disabled
  or stereo scene buses. The test layouts satisfy these requirements.
- The zero-frame test matches the remaining-MIDI loop after sample processing.
  Its transport assertions depend on no supplied playhead, matching the fixture.
- Bypass uses the existing eight-callback drain before unconditional clearing;
  testing the ninth callback is consistent with that source path. Reset calls
  `stopSound()` and resets `blockPos`.

The five cases cover callback segmentation and MIDI sample offsets, scene-output
clearing, aliased input with explicit/automatic latency, zero-frame callbacks and
host bypass/reset. They compare deterministic captures within the candidate
processor. They are not a baseline processor comparison, actual VST3 host loading,
CLAP event-transport equivalence proof, or real-time underrun measurement.
