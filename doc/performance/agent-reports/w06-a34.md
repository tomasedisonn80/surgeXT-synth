## Finding

No claim-inflating implementation defect was found in the current fixture and
paired-runner paths. Their results support a matched **offline wall-time**
comparison, with the qualifications below. They do not measure DAW CPU meters,
callback deadlines, or the cost of the optimized JUCE output-pointer path.

## Timing and fixture construction

`src/performance/CpuBenchmark.cpp::run` constructs a fresh engine for every
repetition. `configure` reseeds the storage generator, noise generator, and C RNG,
prerolls 128 engine blocks, then reseeds again before the note events. The
constructor's time-based C RNG seed is therefore replaced before the measured
fixture starts. Repeated fingerprints remain the check that the complete chosen
fixture actually reproduced; reseeding alone is not proof for arbitrary patches.

The `steady_clock` interval in `renderWindow` contains `SurgeSynthesizer::process`,
interleaving copies into an already allocated PCM vector, and PPQ advancement.
Construction, patch/effect loading, preroll, note-on/off dispatch, PCM allocation,
file writing, finiteness/statistics scans, and hashing occur outside the interval.
Held and tail intervals are timed separately. Durations round upward to complete
engine blocks, and the reports retain the actual audio duration.

Effects use the real global FX slot and parameter-loading path. Loading is checked
before timing; nontrivial coefficient inputs are assigned. The parametric EQ
defaults to full wet, graphic EQ bands default enabled, and the Conditioner
fixture explicitly enables its high-pass section. Active-formula routing failures
throw. The existing baseline smoke JSON has nonzero peaks for all nine non-idle
scenarios and effect fingerprints different from `init-8`; this is fixture
sanity evidence only, not a new timing result.

`requested_notes` means MIDI note requests. It is not an assertion about active
voice count: dual scenes can produce additional voices, and a supplied patch may
use mono modes or other voice settings. Report tables should retain that wording.
The tail result includes the complete fixed post-release interval, including any
portion that has already become idle. It is not a worst-case long-tail estimate.

## Pairing and statistics

`scripts/performance/run_comparison.py::execution_order` alternates complete
baseline/candidate invocations in AB, BA, AB order. Each child renders one
repetition. Raw reports and logs are retained. `merge_reports` validates each
report, matches parameters/scenario sets and fingerprints, and recomputes
medians/minima/maxima from the raw timings without discarding samples.

The reported percentage is exactly:

`100 * (1 - median(candidate wall times) / median(baseline wall times))`

It is a ratio of medians, not the median of individual paired percentage changes.
Seven rounds produce four AB and three BA invocations. Alternation reduces simple
ordering bias; it does not establish fixed clocks, exclusive hardware, or a
statistical confidence bound. Retain the raw arrays and ranges, and interpret
small differences against the observed variability.

## Audio binding and validation

The native benchmark rejects nonfinite samples. The strict comparator rejects
invalid/nonfinite timing values, false success/determinism flags, duplicate JSON
keys/scenario names, metadata mismatches, inconsistent recomputed summaries, and
fingerprint drift within or across reports.

Only the first pair writes complete PCM. At completion those files are compared
byte-for-byte, checked for finiteness and expected length, bound to their FNV
fingerprints, and assigned a SHA-256 digest. Later rounds retain matching FNV
fingerprints rather than complete PCM. Do not describe all rounds as independently
compared complete audio files.

Zero peak/RMS is intentionally accepted because `idle` is silent. Before publishing
final measurements, independently check that non-idle fixtures have nonzero peaks
and that the three effect fixtures differ from `init-8`. The `all` runner verifies
matching scenario sets but does not itself require the ten standard names; the
current native source emits all ten, and the smoke gate checks that exact set.
The final results should explicitly list all measured names and note counts.

## Provenance and limits

The runner hashes both executable files before execution, before each invocation,
and at completion. Optional patches receive the same identity checks. It records
exact command arrays/order, paths, return codes, timestamps, OS/CPU labels and
affinity. These checks help prevent accidental binary or patch replacement during
an experiment.

The native report's compiler, configuration, Lua request and LTO request are
useful comparisons, but they do not establish the effective compiler/linker flags
or Lua implementation. `source_description` hashes the current harness/scripts;
its tracked Git diff omits untracked files, including a newly added production
header before staging. It explicitly does not attest the binary build inputs.
Retain a separate build manifest with exact commands/effective flags, baseline
commit, candidate source hashes for every changed production/header/harness file,
pinned submodule revisions, and binary SHA-256 values. Confirm the actual baseline
and candidate harness files match.

The floating-point guard encloses configuration/preroll/rendering, while initial
engine construction and the first `setSamplerate` occur before it. Same-machine
comparison still assumes a controlled surrounding environment. Ambient user
defaults, data assets, and external tuning services are not fully inventoried by
the runner. PUC Lua measurements must be labelled as PUC; they do not establish
LuaJIT performance. This headless benchmark also excludes native processor/UI and
host callback overhead.

## Recommended final results fields

- Baseline commit and candidate source/build identity; exact binaries and harness
  SHA-256 values, effective Release/LTO/ISA/compiler/Lua configuration.
- Machine context and whether other work ran concurrently.
- Sample rate, block size, seed, preroll, actual held/tail lengths, rounds/order,
  scenario names, and requested MIDI note counts.
- Per-scenario baseline/candidate median wall seconds, raw ranges, and the ratio
  of medians above; include regressions and results within timing noise.
- Separate first-pair full-PCM/SHA-256 verification, later-round fingerprint
  equality, and the independent 63-fixture lifecycle comparison.
- Explicit pending platform/host checks, with no extrapolation to all patches,
  machines, DAWs, buffer sizes, or real-time deadline reliability.
