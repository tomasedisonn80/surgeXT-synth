## Proposed five passes, every one of 1,000 presets

The minimum acceptance unit is a **preset hash plus a versioned test scenario**, not a category-level aggregate. Write a row per preset per pass with `pass/fail/not_run`, metrics, failure reason, engine commit/build settings, file SHA-256, scenario version, sample rate, note numbers, velocity, tempo and macros. A later preset change invalidates its prior audio passes.

### 1. Static and native serialization integrity

Check exactly 10 categories x100, unique names/IDs, valid FXP header (`CcnK`, `FPCh`, `cjs3`; native loader `SurgeSynthesizerIO.cpp:261-299`), bounds and finite numeric values, revision, correct binary lengths, complete documented macro routings and category tags. All parameter changes must affect active signal paths; reject differences limited to metadata or inactive scenes/oscillators. Check deterministic generator output. Load every file through the real engine, assert success, expected identity, no load errors; native-save to a temporary file and reload it, compare meaningful parameter/modulation state rather than raw byte equality. Check embedded wavetable data / packaged references, never author-machine absolute paths. Native load alone can silently clamp or ignore some values; compare the semantic state to intended values.

### 2. Default audio, signal integrity and release

For each preset at 48 kHz, default macros, representative note (category-specific), velocity96: render 4 seconds held plus sufficient category-specific release (at least 2 s; pads/long FX may need more). Check finite samples, both-channel RMS/peak, sample peak, oversampled true peak if implemented, persistent DC on held region, render duration, silence and post-release trend. Suggested hard defects: any NaN/Inf; absolute sample >=1.0; sustained unintended silence; persistent DC >0.01 (about -40 dBFS) after excluding attack; stuck nondecaying tail beyond documented bound. Suggested **design targets**: normal default peak <=-6 dBFS and stress peak <=-1 dBFS; RMS and onset limits must be category-specific, not arbitrary universal loudness normalization. A one-shot can naturally become silent while the key is held. Deliberately long ambient tails should be measured and documented, not misclassified as stuck notes.

### 3. Musical articulation and register

At each preset's documented low/mid/high usable register, render velocities32,80,127 with release and a representative chord/phrase. For monophonic bass/lead, test legato/retrigger and correct last-note behavior, not mandatory polyphony. For polyphonic patches test triad/seventh voicings and release. Check audible intended range, finite/headroom metrics, monotonic or intentionally documented velocity effect, clean retriggering, no unintended transposition/tempo drift. Do not mandate bright highs for dark drones or sustained output for plucks. For tuned keys/plucks/bells use fundamental estimation only when a stable identifiable fundamental exists; inharmonic bells/noise FX should not fail a forced pitch detector. This pass establishes coverage of a declared range, not all 128 notes.

### 4. Expressive, tempo and polyphony extremes

For every configured macro, render baseline and both endpoints individually, then a documented worst-case combination. Verify at least one intended parameter changes, measured audio changes beyond baseline stochastic variation, finite output and gain limits. Exercise mod wheel, aftertouch, sustain and pitch bend where supported; compare state before/after and ensure release does not leave notes held. Pulses/tempo-synced FX: 60,120,180 BPM with actual host time advance; other patches need tempo invariance check. Stress declared polyphony (e.g. 8 or16 notes) and rapid note changes, measure deadline performance as advisory on this host. State CPU/compiler/sample-rate/block-size; no generic claim of realtime reliability on every machine. True high-rate support needs a secondary sample-rate render (44.1 or96 kHz) for every preset if that claim is made.

### 5. Independent bank/packaging and listening-readiness audit

Have reviewers independently check every preset's name/use case/range/control documentation against its semantic state and metrics. Exact semantic-hash duplicates are hard failures. Compare pairwise fingerprints (spectral-band energy, centroid, envelope, pitch class/noisiness, modulation-rate descriptors) and review the nearest neighbors; similar variants are allowed when their differences have documented musical purpose, but 1,000 files made by tiny irrelevant parameter jitter are not 1,000 meaningfully distinct designs. Check all 1,000 files in staged/install data, native factory browser discovery counts and hashes; load representative installed paths and keep the all-file native checks against staged paths where feasible. Every preset has an audition WAV/preview or can be deterministically rendered from a supplied MIDI scenario. **Automated/agent audit is not human listening.** Keep `human_audition: pending` unless a person actually listens; a listening rubric covers tone, musical identity, noise/artifacts, balance, controllability and fit under dialogue. Never mark Hollywood-composer endorsement or universal genre suitability as tested.

## Implementation practicality

Use a bounded CLI/native worker operating over an explicit manifest. Run independent synth instances/process workers in modest parallelism. A complete bank with 30-60 virtual seconds of material per preset means 8.3-16.7 hours of synthesized timeline, but offline speed depends heavily on effects/unison. Benchmark the first10 presets, then estimate time; do not substitute sampling20 presets while claiming all1,000 passes. Reuse buffers and retain concise metrics for every scenario; keep representative WAVs plus all failing outputs to control repository size. Render all final files after repairs, not merely their archetype. Reject or repair failures; report unexecuted checks as unexecuted.
