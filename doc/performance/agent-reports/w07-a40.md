- Wave: 7 of 10. Role: systems engineer and VST compiler specialist.

## Result

The recorded builds use matching options for the code being compared. All **86
`surge-common` object rules** have identical configuration, definitions, compiler
flags and include paths after normalizing only their source/build directory roots.
The candidate enables the existing unit-test target while the baseline does not;
that difference does not change these common-engine options.

`ninja -t commands src/performance/surge-cpu-bench` was used only to expand command
strings; it does not execute the build. The artifact retains both the actual and
normalized commands, per-command SHA-256 values, selected cache entries, compiler
driver identity, and CMake compiler-record, cache and Ninja-file SHA-256 values.

| Expanded command | Normalized baseline/candidate match |
| --- | --- |
| `SurgeSynthesizer.cpp` compilation | Yes |
| `ConditionerEffect.cpp` compilation | Yes |
| `CpuBenchmark.cpp` compilation | Yes |
| `surge-cpu-bench` final link | Yes |

Both builds record GNU C++ **14.2.0**, Release **`-O3 -DNDEBUG`**, C++20, and
**`-flto=auto -fno-fat-lto-objects`** at compilation and final linking. Engine and
benchmark compilation uses **`-msse4.1 -mfpmath=sse`**. No `-ffast-math`, `-Ofast`,
`-march=native`, `-mtune=native` or `-mavx*` option appears in any of the 86 common
object rules or the three representative compilation commands.

Both explicitly select `SURGE_LUA_IMPL=puc`, define `HAS_LUA=1`, and link
`libs/lua/liblua-5.2.4.a`. This is stronger evidence of the effective Lua backend
than the benchmark's requested-backend label alone.

The compiler path resolves to `/usr/bin/x86_64-linux-gnu-g++-14` in both builds.
Its driver SHA-256 is
`6b3696e4dcb85e1c949c732a02befa50e3983ecf94ce7e8e58d9d503b954b79d`.

## Interpretation and limits

The exact existing `-fno-math-errno`, `-fno-trapping-math` and warning options are
retained in the artifact; this review changed none of them. Matching options do
not themselves establish a CPU reduction or binary provenance. Source and native
executable hashes are retained separately in
[build-provenance.json](../evidence/build-provenance.json).

The conclusion applies to the recorded Linux x86_64 headless PUC builds. It does
not establish effective flags for Windows/macOS/ARM distributions, LuaJIT builds,
or the native JUCE plugin wrapper. Those have separate platform CI coverage.
