## Measurement boundaries

In `CpuBenchmark.cpp`, `threadCpuSeconds()` uses Linux
`CLOCK_THREAD_CPUTIME_ID`, checks the return code and rejects invalid readings.
`run()` queries that clock only when `--thread-output` is present. The start CPU
read precedes the steady-clock start, and the end CPU read follows the
steady-clock end. Neither clock is read inside the per-block render loop.

The CPU interval includes the same engine processing, preallocated PCM copies
and transport advancement as the wall interval, plus the two wall-clock reads
and small surrounding clock instrumentation. Engine creation, fixture setup,
note-on/release events, file output, hashing and audio statistics remain outside
both render windows. CPU charged to other threads and time spent descheduled
are outside this thread-clock measure. Frequency, cache, shared-core and
instrumentation effects remain; CPU time is not a hardware cycle count.

## Evidence bindings and calculation

`thread_clock.validate_report()` first validates the wall report, then requires
the exact sidecar schema, tool/clock names and success flag. Integer metadata
types and values, scenario coverage, held/released durations, repetition
counts and every recorded PCM fingerprint must match that wall report. CPU
arrays must have the expected length and contain positive finite numbers.
Duplicate JSON fields are rejected by the shared report reader.

`run_comparison.py` retains raw one-repetition wall and CPU reports, command
order, executable hashes and CPU-sidecar SHA-256 values. It checks unchanged
executables around the experiment and validates audio consistency within and
between sides. Complete PCM from the first pair must pass the existing
byte/length/finiteness/fingerprint checks before the final CPU comparison is
written. Later rounds use their matching recorded FNV fingerprints; they do
not receive full-file PCM verification.

Eight explicitly requested rounds produce four AB and four BA rounds through
`execution_order()`. The runner's default remains seven, so the final command
must retain `--rounds 8`. `thread_clock.compare_reports()` recomputes raw arrays,
medians, ranges and `100 * (1 - median(candidate) / median(baseline))`. It does
not substitute a median of paired ratios. Negative results remain in the
summary. A successful result validates comparable evidence and the required
audio checks; it does not assert an improvement or statistical significance.

## Failure and output handling

Native preflight rejects unavailable clocks/platforms and aliases between the
sidecar, wall report, input patch and generated PCM before opening outputs.
Canonical-path and file-equivalence checks cover direct paths, symlinks and
hardlinks. Runtime CPU intervals must remain positive and finite.

Native outputs are incremental, so a failed process can leave partial files.
The paired runner requires a new or empty directory, zero child exit status,
strict complete reports and valid success fields. Failures retain non-success
provenance and diagnostics; missing or corrupt CPU evidence cannot produce a
successful final CPU summary. A separately valid wall result is not by itself
proof that the complete CPU experiment succeeded.
