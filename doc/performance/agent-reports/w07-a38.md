# Wave 7 / agent 38 — final callback source review

Role: systems engineer and VST/CLAP callback specialist. Read `AGENTS.md` and

`reset`, the five `XTTestCpuProcessing.cpp` cases, and the pinned JUCE buffer and
VST3 wrapper implementations. No production correctness blocker was found.

## Source findings

- `isBusesLayoutSupported` permits a stereo or disabled main output, mono/stereo
  or disabled input, and independently disabled/stereo scene buses. The callback
  returns after clearing when the main output is disabled/non-stereo or the
  supplied buffer lacks the two main channels. Cached main pointers are reached
  only after those guards. Hosts still must supply storage matching the complete
  enabled bus layout; these changes do not validate arbitrary malformed buffers.
- `getBusBuffer` returns callback-local views of the supplied channel pointers.
  The callback does not resize those views or the master buffer while pointers
  are used. Nothing stores the new pointers in processor state. Scene clearing
  precedes pointer acquisition; no further scene clear occurs before writes.
- JUCE `getWritePointer` changes the view's cleared flag without modifying audio
  samples. Acquiring inactive scene pointers therefore leaves the previously
  cleared samples zero. Acquisition is skipped for zero-sample callbacks.
- MIDI application remains before each corresponding sample's engine/input work.
  Aligned input copies and compensated input capture still precede aliased output
  writes. Mono duplication, `inputIsLatent` selection, `blockPos` advancement and
  32-sample engine processing retain their original order.
- `activateExtraOutputs` remains a per-sample condition, so caching valid scene
  pointers does not freeze its value at callback entry. Independently enabled
  scene buses are checked separately. No thread-safety claim is made for an
  unsynchronized external write to this pre-existing ordinary boolean.
- Zero-sample callbacks skip pointer writes and engine processing; the trailing
  MIDI loop still applies pending events. This means event application, not
  clearing the caller's MIDI container. Existing transport/playhead handling
  remains outside the changed loop.
- Bypass stop/fade countdown, terminal buffer clearing and resume flags precede
  the pointer cache and remain unchanged. `reset()` restores `blockPos` and calls
  `stopSound`; there are no persistent pointers to invalidate.

## Bypass and CLAP distinction

`SurgeSynthProcessor` does not override `processBlockBypassed`. It returns a
non-null bypass parameter. The pinned VST3 wrapper explicitly routes such
processors through `processBlock`, leaving the processor to implement that
parameter's bypass behavior. The new bypass test exercises this appropriate
parameter path. It does not exercise JUCE's inherited `processBlockBypassed`.
The separate `clap_direct_process` implementation is unchanged and does not use
the new JUCE pointer cache.

## Test evidence and limits

The five cases cover callback segmentation and fixed MIDI timelines, stereo main
and both scene buses, inactive extra-output silence, aliased mono/stereo inputs
in both latency modes, automatic latency selection from odd block sizes,
zero-sample MIDI/transport behavior, bypass clearing and reset. Guarded host
storage and overlapping callback-buffer lifetimes make stale pointer retention
and boundary writes observable. Audio comparisons check segmentation invariance
with the existing 32-sample engine cadence; they do not establish finer engine
event resolution.

The tests do not independently exercise one scene bus enabled while the other is
disabled, change `activateExtraOutputs` inside a callback, run a commercial host
or CLAP direct processing, or assert a nonzero resumed-note magnitude after
bypass. These are limits on reported coverage, not defects introduced by the
reviewed pointer change. Native execution remains the coordinator/CI's gate;
this review did not compile or run the processor tests or measure callback CPU.
