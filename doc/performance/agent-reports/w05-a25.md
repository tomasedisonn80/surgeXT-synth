# Wave 5, agent 25 — coefficient-cache floating-point review

Role: systems engineer and VST DSP specialist. Initially a source review of the
working tree; after reporting a concrete issue, this agent implemented the
coordinator-authorized fix described below. No native builds, benchmarks,
commits, or pushes were performed by this agent.

## Finding and implemented resolution

The cache keys cover parameter values and storage tables, but the reviewed
version does not cover a change in the floating-point control environment
between otherwise identical processing calls. This matters in two current
plugin paths:

- `SurgefxAudioProcessor::processBlock` uses `juce::ScopedNoDenormals`, which sets
  denormal handling and preserves the caller's rounding mode.
- The pinned `sst::plugininfra::cpufeatures::FPUStateGuard` sets nearest SSE
  rounding on x86, but its AArch64 branch only sets FPCR's flush-to-zero bit.

If a subsequent callback has a different rounding mode, the original effects
recalculate coefficient targets in that callback's environment. The reviewed
caches retain targets calculated in the previous environment when inputs, rate,
and table generation are unchanged. The existing adversarial init/table rebuild
fixtures do not by themselves exercise this mode-only transition. The
coordinator was notified before measurements were finalized.

Recommended fix: include a cheap read-only floating-point control key at the
existing coefficient-update cadence, and add a baseline differential fixture
that changes callback rounding without resetting the effect, rate, parameters,
or storage tables. Restore the test's original environment after each fixture.
Do not change the plugin's existing arithmetic environment merely to make the
cache valid.

At the coordinator's request, the fix was implemented in the new
`src/common/dsp/effects/CoefficientCache.h` and wired into Conditioner,
GraphicEQ11Band, and ParametricEQ3Band. Each effect retains a `uint64_t` key and
refreshes all its targets when the environment changes. ARM64/ARM64EC uses
actual FPCR, native x86 reads the masked MXCSR, and unsupported targets always
recompute. Reads do not alter the environment. Existing parameter/rate/table
keys, reset hooks, first-callback invalidation, and control cadence remain.

Scoped whitespace verification passed after the edits. Native build,
mode-transition differential execution, and platform compiler coverage remain
with the coordinator; this report does not claim those checks have passed.

### Implementation guidance supplied to the coordinator

- Native x86: `_mm_getcsr() & 0xe040u` includes rounding, DAZ, and FTZ while
  excluding sticky exception flags. GNU/Clang x86 builds already specify
  `-mfpmath=sse` in root `CMakeLists.txt`. If preserving unusual x87/libm control
  modes is within the supported contract, account for those separately rather
  than claiming MXCSR represents x87 state.
- GCC/Clang ARM64: read actual FPCR using the existing `MRS` pattern in
  `libs/sst/sst-plugininfra/src/cpufeatures.cpp`. Full FPCR is a conservative
  control key; cumulative exception status resides in FPSR.
- MSVC ARM64/ARM64EC: `_ReadStatusReg(ARM64_FPCR)` reads FPCR. Its architectural
  encoding is `ARM64_SYSREG(3, 3, 4, 4, 0)`, or `0x5a20`. Select native ARM
  before x86 macro branches because ARM64EC also exposes x64 compatibility
  macros. Cross-platform CI is still required to verify compiler/header support.
- Do not use the pinned SIMDE `simde_mm_getcsr()` as an ARM denormal-state key:
  `libs/simde/simde/x86/sse.h` maps non-x86 reads to rounding mode alone and
  reports flush-zero off in its non-native implementation.
- For unhandled targets, retaining uncached calculations is safer than claiming
  an incomplete key is valid. No per-block environment save/restore is needed.

Primary API references consulted: [Microsoft ARM64 intrinsics](https://learn.microsoft.com/cpp/intrinsics/arm64-intrinsics)
and [LLVM ARM64 intrinsic declarations](https://clang.llvm.org/doxygen/arm64intr_8h_source.html).

| --- | --- | --- |

| Three-band EQ | Per-band frequency/bandwidth/gain, `dsamplerate_inv`, `table_pitch_ignoring_tuning`, `table_dB`, arithmetic environment | Values, rate, table generation covered; environment finding above |
| Eleven-band EQ | Per-band gain, fixed Hz/bandwidth, `dsamplerate_inv`, `table_dB`, arithmetic environment | Values, rate, table generation covered; environment finding above |

`BiquadFilter::calc_omega` uses the tuning-independent pitch table, not the
user's retuned pitch table. A repository search found the coefficient source
tables assigned in `SurgeStorage::init_tables()`. That function now increments
the generation after rebuilding them. Consequently direct
`SurgeStorage::setSamplerate()` calls—including the same numeric rate from the
effects plugin—and `retuneTo12TETScaleC261Mapping()` invalidate these caches.
Ordinary nonstandard retuning does not alter the tuning-independent sources.

The pinned Biquad implementation confirms that `vlag::newValue()` only assigns
the target. Its `process_block()` still advances coefficient smoothing sample
by sample. The changed effects continue processing each enabled filter at the
original cadence, including ringout. Their coefficient checks still run for
deactivated bands, so reactivation does not lose intermediate target updates.

Both EQ initializers invalidate before their original suspend sequence, and
Conditioner invalidates after initialization so its first process call
recalculates under the callback environment. `suspend()` delegates to `init()`;
the added `sampleRateReset()` hooks invalidate without resetting audio history.

The parameter comparisons distinguish signed zeros and bitwise-distinct
subnormals, and never accept NaN as unchanged. Finite sample rates accepted by
the storage API are positive, so the EQ numeric rate comparison does not lose
a reachable positive/negative-zero transition.

## Realtime and concurrency assessment

The generation check adds one relaxed atomic load per existing coefficient
update, not a read-modify-write in the audio callback. Rebuilds increment once
outside the normal unchanged-parameter path. The fixed cache storage introduces
no allocation or explicit lock. The generation is invalidation metadata, not
synchronization for concurrent non-atomic table mutation; the existing
serialization requirement remains.

No CPU reduction percentage is inferred from this review. Quantitative claims
require the coordinator's quiet, paired measurements after the environment-key
fix and native baseline comparison.
