# Agent 43 — coefficient-cache performance diagnosis

Wave 8 of 10. Role: systems engineer and VST DSP performance specialist.
Reviewed the frozen implementation published as
`ae551fa2a4bd95efe21633f1c41a9326c8ef5df0` and the initial seven-round 48 kHz
experiment. This assignment used source inspection and existing JSON only; no
native program, compiler, build or new timing experiment was run. Production
files were not changed.

## Finding

No source-level defect was found that would make these steady effect fixtures
miss their coefficient caches continuously. Cache hits are expected after the
warmup. That is a source inference, not a measured hit-count assertion. The
initial timing data do not establish a CPU improvement, and no performance
claim follows merely from this inference.

### Why the keys should remain stable

- `CpuBenchmark.cpp::configure` loads the real effect, assigns finite constant
  coefficients, and performs 128 warmup blocks. Its timed loop changes neither
  coefficient parameters nor sample rate, tuning, effect type or floating-point
  mode. The effects use the post-modulation `pd_float` values; these fixtures add
  no effect modulation routes.
- `SurgeStorage::coefficientTableGeneration` increments only at completion of
  `init_tables()`. The constructor, sample-rate setter and standard-tuning reset
  reach that function, but the steady timed benchmark does not call those reset
  paths. The relaxed atomic load is not an atomic read-modify-write.
- The available GNU/x86 build defines `SST_SIMD_NATIVE_X86`. Its environment key
  reads MXCSR rounding/FTZ/DAZ and x87 precision/rounding. Sticky exception status
  is excluded, so ordinary floating-point arithmetic does not invalidate the
  cache just by raising an inexact or underflow flag. The floating-point guard
  spans configuration and the timed rendering.
- Conditioner marks its cache valid after `setvars(false)`. Its initialization
  invalidation is intentional, but initialization is not repeated per block.
  Both EQs likewise preserve validity until a real reset or changed key.
- `Effect::process_ringout` chooses `process` or `process_only_control`; it does
  not call `init` or `suspend`. `SurgeSynthesizer::processControl` clears reload
  and suspend requests after applying them. There is no unconditional per-block
  reset in the reviewed path.

## Cost that remains

The cache omits target calculations, while all required sample processing and
smoothing remain. Conditioner still performs lookahead, detector dynamics,
stereo conversion, filter processing and gain work. Each EQ still runs its
enabled filters for every sample. The original EQ target-update cadence was
already once per eight blocks, so the saved calculations are amortized over 256
samples.

Every eligible update now pays for one generation load, the native floating-point
control reads, validity/rate comparisons and exact input comparisons. Conditioner
does this once per processed block; EQs do it once per eight processed blocks.
The relative cost of that bookkeeping versus the removed coefficient math has
not been isolated by the initial whole-engine experiment. Oscillators, voices,
modulation and PCM copying also remain in its timed region.

The inspected `BiquadFilter::coeff_orfanidisEQ` still performs the target math
for non-unity gains; there is no pre-existing hidden equivalent target cache in
that routine. The configured nonzero effect gains and different rendered audio
fingerprints make silent or neutral fixtures an implausible explanation for the
initial result.

## Object layout

The new Conditioner members precede its detector/history fields, the EQ cache
members precede `bi`, and the storage generation precedes its sample-rate and
later members. These additions can shift subsequent offsets and change cache-line
placement or allocation size. Existing explicit SIMD alignments remain intact.
Source alone cannot determine whether these layout changes help or hurt this
machine; they are not a diagnosed cause of the timing results. Moving members
solely to obtain a favorable run would require a new controlled comparison and
audio verification, and is not recommended from the initial noisy data.

## Bounded diagnostic if the longer comparison is still inconclusive

Use an identical temporary effect-only harness linked against the existing
baseline and candidate common engines. Construct the real three effects through
the ordinary setup path and use their current fixture parameters and FPU guard.
After warmup, feed a precomputed finite stereo block into `Effect::process`,
resetting the input block before each call. Preserve the normal EQ control
cadence. Record output for full-byte comparison and time a fixed, sufficiently
long block count in balanced AB/BA order on the same CPU.

This should measure the whole effect, including its normal filters and dynamics,
without oscillator/voice/control costs. Do not time a loop that only calls
`setvars(false)` and observes the final state: repeated overwritten coefficient
targets could make compiler elimination or hoisting distort that microbenchmark.
Retain runtime effect dispatch and inspect effective compiler options. An
untimed diagnostic pass can additionally verify that public `pd_float` values,
storage generation and environment keys remain unchanged.

This diagnostic could separate small whole-synth gains from a lack of effect
benefit, but cannot establish a DAW-level CPU reduction. It was proposed only;
the coordinator did not authorize implementation or execution in this review.
